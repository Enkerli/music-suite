# Twirl — accessibility record

*2026-10-24. Method: [mgifford/accessibility-skills](https://github.com/mgifford/accessibility-skills)
(`cli-audit`, then `ci-cd`, `keyboard`, `touch-pointer`, `aria-live-regions`,
`light-dark-mode`, `user-personalization`), the same skill set the suite
used for Serpe (docs/DESIGN_PASS_2_SERPE.md). Target: WCAG 2.2 AA. This is a
record of findings and fixes, **not a conformance claim.***

## How it was checked

1. **`cli-audit`** (`cli-inspect.mjs`: Playwright + axe-core 4.14, default
   rules) on the first screen, served locally exactly as Pages serves it.
   The skill's accessibility-tree snapshot failed on Playwright 1.63, which
   no longer has `page.accessibility`, so the tree was read with
   `locator.ariaSnapshot()` instead.
2. **An axe sweep of eleven states × light and dark** (tags `wcag2a`,
   `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, `best-practice`), because
   the skill's CI guidance is to scan "meaningful states after the page is
   ready AND after relevant interaction", not just the first screen.
3. **What axe can't see:** keyboard paths, focus movement, gesture
   alternatives, motion preferences, hit-testing of overlapping layers,
   glyph contrast. Checked by hand in headless Chromium, then written as
   tests.

All of it now runs as `apps/twirl/test/twirl.a11y.test.js` (40 tests) on
every push, via `npm test` in `tests.yml`.

## Findings and what was done

Per the `cli-audit` reporting rules, every automated finding below is
`evidence_status: automated-indicator`, `handling: review`. No person
using assistive technology has confirmed any of them. Severity uses the
skills' scale (Critical / Serious / Moderate / Minor), judged on the task;
it is not axe's label. WCAG mappings come from the axe rule's documented
tags, or from the named skill rule.

Also checked, and fine as they stand:

- **Glyph contrast against the paper** (non-text, 3:1 needed). In light:
  pluck 3.87, bell 3.85, blip 4.51, drum 3.23, shaker 3.55, playhead 5.27.
  In dark: all above 6.7. Voices never rely on colour alone: each also has
  its own shape (● ○ ▲ ■ ◆).
- **Grid lines** are guides at about 1.3:1 and not needed to play. The
  octave lines carry a text label at 5.1:1.
- **Status messages** (toasts) are `role=status`.

## Still not tested (handed off)

- **Screen readers** (VoiceOver on iPad and Mac, NVDA, Orca on Linux).
  The tree is sensible; what it *sounds* like hasn't been heard.
- **Drawing is path-dependent input**, the WCAG 2.1.1 exception. The
  keyboard routes (Toybox, digits, arrows, settings) give the music without
  the drawing. Whether that is a *good* experience for someone who can't
  draw is a design question, not a checkbox.
- **Real touch** on iPad and phone: target spacing in the 24–44 px band,
  pinch near the screen edges, Pencil pressure.
- **Forced colours / high contrast**: the sheet is a canvas, so it won't
  follow forced colours. Not yet looked at.
- **Zoom and reflow at 400%** and **text spacing**: the UI is mostly fixed
  panels over a full-screen canvas. Not yet looked at.
- **WebKit**: the tests run in Chromium only. iPad Safari is a target, so a
  WebKit run (Playwright has one) is the obvious next step.
