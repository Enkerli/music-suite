3Findings

Ordered by user impact, each checked against the personas it hurts most.

F1Two blessed destructive-action idioms — our own docs disagreeHigh — trust
The shipped code (library-browser, Vane, toast.js) uses optimistic delete + undo toast, and the repo's UX audit marks that "SHIPPED" as the Q4 answer. But the Shared Frame spec table (this project, shared-frame/spec.jsx) documents two-tap armed confirm ("✕ → Delete? → commit") as the canonical delete, and MIDIcurator still ships confirm.js. A musician deleting a clip in MIDIcurator, a preset in Vane, and a pattern in Serpe meets three behaviours.
Personas4 · Producer7 · Systematic maker — #7's brief is literally "I need to know what will happen when I click something." RecommendRe-affirm one idiom: undo toast for recoverable item deletes (the shipped pattern); two-tap armed confirm reserved for genuinely unrecoverable acts (clearing all lanes, panic-adjacent). Update spec.jsx + retire confirm.js from MIDIcurator delete paths. EffortDoc edit + one MIDIcurator migration. Small.
F2Workspace shipped without the frame — the checklist has a gapHigh — process
The newest surface (promoted from staging 2026-07-19) imports es tokens + components but hardcodes data-theme="light", has no theme toggle, no cluster, no density mode. Nothing in DESIGN.md's release checklist says "mount the global cluster" — so the first app born after the frame shipped… doesn't wear it. This will recur with every new module.
Personas1 · Wind performer5 · Accessibility-first — no dark mode and no density toggle on the one surface meant for live, multi-module use. RecommendAdd "shared frame mounted (cluster · enkerli.theme · density target)" as a line in the DESIGN.md release checklist; retrofit Workspace (its main.js already injects the right CSS — this is a ~20-line change). EffortSmall, unblocked.
F3PickPCS has no theme control at allMedium
Zero theme code in PickPCS.jsx: dark mode arrives only via the tokens' OS-preference fallback and cannot be chosen — the only suite app where the person's stored enkerli.theme choice is ignored. Its MIDI send is a bare push button with no port visibility ("push-button-without-a-bar" from audit v1 — still true).
Personas3 · Theory explorer5 · Accessibility-first — an educator projecting to a class can't force light; contrast preference is silently dropped. RecommendMount the cluster (theme + MIDI-out slot; no density/Library needed). PickPCS being mostly embedded in PitchFold makes this doubly worthwhile: the same chrome then appears in both hosts. EffortSmall — it already sits on es vars.
F4PitchFold: converged values, divergent mechanismMedium
Tokens are now es-verbatim and the theme key is shared — good. But the chrome is still hand-rolled: its own tab bar, its own theme-toggle placement inside the tab row, its own DeviceSel selects (no LED, no status word, no remember-by-name), no cluster, no Library (chord-pad banks live only in APVTS state). It also duplicates resolvedTheme() inline rather than importing theme.js — the third private copy of that logic (Vane's is excused by its no-modules constraint; PitchFold bundles with esbuild and has no such excuse).
Personas1 · Wind performer4 · Producer — device state legible at a glance is exactly what the es-device-bar's LED + status word provide. RecommendAdopt cluster (theme · MIDI · density) in the header; swap DeviceSel for the cluster's device popover; wire pad banks into the library-browser as patch-kind items (the named Track-B path). Import theme.js instead of the inline copy. EffortMedium — the WebView build already consumes @enkerli/ui in siblings.
F5Vane: converged by hand — drift is now a build concern, not a design oneLow
Vane did what the pass asked, the constraint-respecting way: literals synced byte-for-byte, with a comment contract ("if tokens.css changes, re-sync"). That contract is manual. One token change upstream (like the --es-fg-muted AA bump that already happened once) silently un-syncs Vane.
RecommendA tiny check script (compare Vane's :root literals to tokens.css, run in CI next to the contrast audit) turns the comment contract into a machine one. No UI change. EffortSmall, unblocked.
F6DrawnQurve is now the last un-converged app — and one doc miscounts its platformsMedium
The webapp still carries its own PAPER objects with pre-convergence values, no persisted theme, no frame; qurves remain trapped in plugin state chunks (not first-class Library content — the LIBRARY_SPEC finding stands); and the shipping plugin editor is still the native JUCE UI. Meanwhile at least one suite document still claims DrawnQurve is platform-limited — it ships across platforms; the claim should be corrected wherever it appears (README/site/docs sweep).
Personas2 · Grid learner4 · Producer — saved curves you can't browse, name, or carry between hosts. RecommendSequence: (1) sync PAPER values + adopt enkerli.theme (mechanical, mirrors PitchFold's move); (2) make qurves first-class Library items per LIBRARY_SPEC's payloadRef path; (3) frame adoption when the WebUI replaces the native editor. Plus the one-line doc correction now. Effort1 is small; 2 is the design-gated piece; 3 rides the existing WebUI plan.
F7Build-id chrome is still a Vane-only diagnosticLow
__VANE_BUILD__ + chip answered "which build am I looking at?" so well it was blessed as a suite convention in the convergence pass — but no other app knows its build. With ten apps × three runtimes, support conversations need it ("web or plugin? which build?").
Personas7 · Systematic maker — visible state, including the app's own. RecommendA cluster option (build: {id} rendering a fifth, rightmost, non-interactive chip) + the __BUILD_ID__ sed step each build already has a home for. Adopters get it for free. EffortSmall, unblocked.
F8Library reach: the browser exists, three content stores still bypass itMedium
The Q2 deliverable landed and has three real adopters — but MIDIcurator's clip library stays on its own sidebar UI (reasonable: it IS the app; still, its vocabulary should match the browser's — kind badges, facet chips, save wording), Vane's Presets tab remains a parallel implementation of the same pattern, and PitchFold/DrawnQurve content isn't addressable at all (F4/F6).
RecommendDon't force MIDIcurator's sidebar into a drawer; converge its vocabulary (naming, badges, delete idiom per F1). Vane's Presets tab: adopt the browser's config API at the next Vane UI touch — it's the same list + facets + search shape already. EffortVocabulary pass small; Vane swap medium (rides F5's constraint).
F9i18n: the DESIGN.md requirement has one implementation and nine gapsLow — unchanged
Still MIDIcurator-only (i18next). No string extraction elsewhere; DESIGN.md carries the localization-readiness requirement for every release. Unchanged from audit v1 — restated so it doesn't fall off the queue, and because the shared components now bake in English strings ("Library", "Connected", "No devices") that will need a pass-through hook when extraction starts.
RecommendWhen i18n work starts, begin with @enkerli/ui's own strings (an opts.strings table on cluster/browser/toast) so every adopter localizes at once.
F10Tab idiom: two survivorsLow
Vane (Stage · Patch · Matrix · Presets, segmented) and PitchFold (Scale · PickPCS · Pads · Voice · Time, ink-filled buttons) still implement tabs independently with different looks. Exquisite's old triple-disclosure is gone (Library drawer replaced it). One .es-tabs recipe in components.css — even just CSS, no JS — would close the last visual fork.
EffortSmall; fold into F4's PitchFold header work.
