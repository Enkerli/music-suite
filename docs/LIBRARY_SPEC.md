# `@enkerli/library` — the suite content model (specification)

*Drafted 2026-07-01 (sprint objective O5). Specification only — no code
ships with this document. The machine-readable envelope schema lives at
[schemas/library-item.schema.json](schemas/library-item.schema.json).
Every existing content kind was inspected at source before writing the
mapping table in §5.*

## 1. Why, and why this shape

The suite already produces at least ten kinds of user-facing content —
presets, patches, curation profiles, progressions, clips, wavetables,
controller profiles, qurves — each with its own ad-hoc persistence.
What passes for a "library" in most music software is a folder full of
opaque files with names as the only metadata. This spec applies
Library & Information Sciences principles instead:

1. **Identity** — every item has a stable identifier independent of its
   title or file name; renames never orphan references.
2. **Provenance** — where an item came from is recorded, as a chain:
   derived from which items, generated by which app/version, sourced
   from which external material, under what license and on what
   evidence. The suite already has an exemplary in-house precedent:
   `vane-wavetable-library`'s metadata (`licenseClaim` /
   `licenseStatus: needs_local_verification` / license evidence kept
   with the files). **This spec generalizes that discipline; it does
   not invent a new one.**
3. **Authority control** — values that mean something musical or
   technical come from controlled vocabularies, not free text:
   `@enkerli/theory` is the authority for keys, chord qualities, and
   PCS/rhythm masks (leftmost = LSB); `manifold` slugs are the
   authority for controllers; status vocabularies are enumerated.
   Free-text `tags` still exist — controlled and free description are
   both first-class, and they are different fields.
4. **Faceted classification** — items are found by orthogonal facets
   (kind × app × key × mood × status…), not by their position in a
   folder tree. Storage location is an implementation detail.
5. **Collection-level description** — a bank, a profile set, or a
   session's worth of exports is itself a described object, not just a
   directory.
6. **Preservation** — absolute timestamps (ISO 8601), self-identifying
   formats (`format` + `formatVersion`), and checksums for detached
   payloads. Nothing depends on file-system dates or names.
7. **Privacy & rights** — user content stays local by default
   (localStorage / app-data / App Group); export is always an explicit
   act. Every item carries a rights statement: the user's own material
   defaults to the suite's Public Domain stance (CC0), derived material
   carries its upstream attribution and evidence. **The jazz corpus
   never enters any library** — only derived statistics do (standing
   decision).

## 2. The envelope

One JSON envelope wraps every kind. Existing formats become **payloads,
unchanged** — adoption means wrapping, not migrating. (ProgGenie's
existing `{ "format": "proggenie-patch", "version": 1, ... }` headers
already follow the self-identification rule; the envelope lifts that
pattern to the suite level.)

```jsonc
{
  "envelope": "enkerli-library-item",      // constant discriminator
  "envelopeVersion": 1,
  "id": "b7d2…",                            // UUID (crypto.randomUUID)
  "kind": "patch",                          // §4 controlled vocabulary
  "format": "proggenie-patch",              // payload's self-name
  "formatVersion": 1,
  "title": "Warm ballad settings",
  "creator": "user",                         // "user" | app id | external
  "app": "proggenie",                        // producing app (§4)
  "savedAt": "2026-07-01T17:00:00Z",         // ISO 8601, absolute
  "provenance": {
    "generator": { "app": "proggenie", "version": "0.3" },
    "derivedFrom": [                         // chain, optional
      { "id": "…uuid of another item…", "role": "curation-profile" }
    ],
    "sources": [                             // external material, optional
      { "name": "…", "url": "…",
        "licenseClaim": "CC0", "licenseStatus": "verified",
        "licenseEvidence": "…kept where…" }
    ],
    "license": "CC0-1.0"                     // rights of THIS item
  },
  "facets": {                                // controlled, queryable
    "key": "E♭ major",                       // theory-spelled when present
    "status": "draft"                        // stub|draft|complete|verified
  },
  "tags": ["ballad", "warm"],               // free text, user's language
  "payload": { /* the existing format, verbatim */ },
  "payloadRef": {                            // instead of payload, for
    "path": "banks/akwf_flute.wav",          // binary/large content
    "mediaType": "audio/wav",
    "sha256": "…"
  }
}
```

Rules:
- Exactly one of `payload` (inline JSON) or `payloadRef` (detached file
  with checksum) is present.
- A **collection** is an item of `kind: "collection"` whose payload
  lists member ids (+ optional per-member notes). Collections nest.
- Envelope metadata never duplicates payload truth; it *describes*.
  (E.g. a progression's key appears in `facets.key` for querying, but
  the authoritative key is inside the canonical `Progression` payload.)
- IDs are UUIDs; `newId()` in ProgGenie's `library.js` is the pattern.
- Musical values in facets follow suite conventions: spelled keys
  (structural spelling), quality keys from `@enkerli/theory`, any
  PCS/rhythm mask leftmost = LSB.

## 3. Storage profiles (same JSON everywhere)

| Where | Mechanism | Notes |
|---|---|---|
| Browser | localStorage / IndexedDB, one index + items | ProgGenie's `proggenie.library.v1` is the seed |
| Plugin WebView | **file-backed over the bridge** (C++-owned JSON) | `juce://` opaque origin breaks IndexedDB — MIDIcurator's `library.json` already does this correctly |
| Desktop standalone | app-data directory (`userApplicationDataDirectory/<App>/`) | where Vane/Serpe presets live today |
| iPadOS shared | App Group container `group.com.enkerli.suite` | **pending Apple-account provisioning** (plan doc §6 backlog); until then each sandbox is an island |
| Interchange | explicit export: JSON file, or SMF with `MCURATOR:v1 PROG` text-meta | export is a user act; nothing syncs silently |

A library on disk is: `library-index.json` (array of envelopes with
`payloadRef`s, or small inline payloads) + payload files beside it.

## 4. Controlled vocabularies

- `kind`: `progression` · `curation-profile` · `patch` · `clip` ·
  `preset` · `wavetable` · `controller-profile` · `qurve` ·
  `derived-table` · `collection` · `phrase` (an
  `@enkerli/accompaniment` AccompanimentPhrase — a curated or generated
  accompaniment fragment with chord-relative annotations; generated takes
  carry provenance to their source phrase, seed, and engine version)
- `app`: `proggenie` · `midicurator` · `serpe` · `vane` · `drawnqurve` ·
  `pitchfold` · `exquisite-fingerings` · `pickpcs` · `chord-dictionary` ·
  `drums` · `rnd-companion` · `external`
  (`drums` is the synthesised kit, not a windowed app; `rnd-companion` is the
  Cymaforma RND hardware companion, which saves captured seeds as `patch`
  items)
- `facets.status`: `stub` · `draft` · `complete` · `verified`
  (adopted from manifold's schema, which already uses exactly this)
- `provenance.sources[].licenseStatus`: `verified` ·
  `needs_local_verification` · `unverified` (adopted from
  vane-wavetable-library's `sources.json`)
- Extending a vocabulary is a spec change (PR to this file), not an
  app-local invention — that is what makes it an authority.

## 5. Mapping — every existing content kind (verified at source)

| Content kind | Where it lives today | Existing format | Envelope mapping | Gaps found |
|---|---|---|---|---|
| ProgGenie progression documents | localStorage `proggenie.library.v1`: `{id, title, composer, source, savedAt, key, bars, prog}` | canonical `Progression` (theory §7 type) | `kind: progression`; `id/title/savedAt` lift directly; `composer`→payload meta; `key/bars`→facets; `prog`→payload | none — closest existing thing to the envelope already |
| ProgGenie curation profiles | exported JSON `{format:"progression-studio-curation", version:1, savedAt, …weights}` | weight ledger (functional, key-independent) | `kind: curation-profile`; `format/version/savedAt` lift | no `id` today (files are anonymous); envelope adds one |
| ProgGenie patches | exported JSON `{format:"proggenie-patch", version:1, savedAt, params}` | generator parameter set | `kind: patch` | same — no `id` |
| MIDIcurator clip library | C++-owned `library.json` in app-data (bridge round-trip) | clip entries + Apple-Loops metadata | `kind: clip`, one envelope per clip; the file becomes a `library-index.json` | App Group pending → standalone↔AUv3 split (known) |
| Vane presets | files in `userApplicationDataDirectory` via `PresetManager` | per-preset file | `kind: preset`, `payloadRef` | file format not self-identifying; wrap, don't rewrite |
| Serpe presets/scenes | `PresetManager` (ValueTree→XML embedded), app-data or Documents | XML state + name/description | `kind: preset`, `payloadRef` (XML), description→envelope | XML not self-versioned; scenes live only inside state |
| DrawnQurve qurves | **plugin state chunks only** (`getStateInformation`) | opaque binary state | `kind: qurve` — **blocked** | **finding: qurves are not first-class content yet**; no save/load-as-file exists. Queue item for DrawnQurve's WebUI migration |
| vane-wavetable-library | repo: `metadata/sources.json` + `tables.schema.json` + WAV banks | richest metadata in the suite (license evidence, curationStatus, family, morphIntent, analysis) | `kind: wavetable`, `payloadRef` to WAV; its fields map ~1:1 (it inspired §1–§4) | none; it's the model citizen |
| manifold controller profiles | repo: YAML per controller, `schema_version: 0.2`, `meta.slug/category/status` | capability database | `kind: controller-profile`; slug = the authority key other items reference | YAML stays canonical in its repo; envelopes reference, not copy |
| Corpus-derived tables | monorepo `data/transitions.json`, `data/trigrams.json` (+ private `regenerated/`) | derived statistics | `kind: derived-table`; provenance chain: Bunks corpus + Impro-Visor imaginary book (attribute both), extractor version | provenance currently in prose (REGENERATION.md) — envelope makes it structured |
| SMF interchange files | user-chosen locations; `MCURATOR:v1 PROG` text-meta | format-0 SMF carrying a `Progression` | already self-carrying; an envelope with `payloadRef` describes exported copies in a library | none |

## 6. What implementation looks like (staged MVP)

Smallest honest MVP:
1. ✅ **Shipped 2026-07-04** — `@enkerli/library` package: envelope types +
   validation mirroring the schema (drift-guarded by test) + `wrap()/unwrap()`
   for the three ProgGenie kinds, plus the faceted query layer (facet counts,
   controlled-vocabulary autocomplete, similar-by-facets suggestions, index
   round-trip). 45 tests.
2. ProgGenie's `library.js` reads/writes envelopes (its legacy entries
   are mechanically upgradable: same fields, new wrapper).
3. MIDIcurator's `library.json` becomes an envelope index — this is
   also the moment to build its SMF→library import (the App-Group
   inbox's missing half, plan doc §6 backlog).
4. Only then: native apps (Vane/Serpe presets as `payloadRef` wraps),
   and DrawnQurve qurve files once qurves can leave the state chunk.

Non-goals, permanently: cloud sync, accounts, telemetry, DRM, and any
"store." A library is the musician's own material, described well.
