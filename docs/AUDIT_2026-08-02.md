## Open, ranked

### B1. `accompany --rhythm` rejects poly notation *(real dead-end)*

`packages/accompaniment/src/pipeline.ts:144` calls `parseUPI` on `opts.rhythm`,
which comes straight from `msuite accompany --rhythm "<UPI>"` — user input. A
lane-separated rhythm throws `--rhythm "…" did not parse as UPI`, for notation
the rest of the suite plays.

The layering rule is *user input → `parsePolyUPI`; library internals only →
`parseUPI`* (SERPE_DAW_FINDINGS F7). This is the one remaining violation that a
person can reach by typing.

**Recommended:** parse with `parsePolyUPI` and use lane 1, saying so — a
harmonic overlay on a bass line is a single rhythm, so taking lane 1 is honest,
and the current behaviour rejects rather than explains.

### B2. Serpe's library loses the reading for poly patterns *(minor)*

`apps/serpe/main.jsx:1332` and `:1382` parse saved library items with
`parseUPI`. A saved poly pattern gets no `k/n` reading and no long/short foot —
it degrades to nothing rather than crashing, so this is cosmetic, but it is user
data going through the mono parser.

**The other three Serpe call sites are correct and should be left alone:**
`:744` is explicitly guarded (`No '/' in this string, so we have just left
poly`), and `:762` / `:916` are `parseBase` callbacks for `progressiveAt`, whose
base is a single body by definition. The backlog carried these as "×3
unreviewed"; they are reviewed now, and they are right.

### B3a. MIDIcurator — audited 2026-08-02, two real fixes

Same method as Serpe. **The landing state audits clean and proves nothing**:
MIDIcurator opens on an empty library with 16 controls, against 70 once clips
exist. Auditing what a cold `goto` sees would have missed both findings.

With 30 clips loaded:

- **`Download All` failed colour contrast** (serious): white on
  `--mc-success` = 3.33:1, under AA's 4.5. `--mc-success` is
  `--es-dim-expr`, the suite's expression-dimension colour, used elsewhere as a
  FILL with nothing on top — so darkening the shared token would have moved that
  dimension everywhere. Added `--mc-success-surface: #268373` for the case where
  text sits on the fill: same hue and saturation, lightness only, 4.59:1.
- **Every row's kebab announced as "⋯"** — 30 clips, 30 identical stops, no way
  to tell which row. Axe passes this, because the button HAS a name; it is
  exactly what the accessibility-tree pass exists to catch. Now
  `Actions for <clip name>`. The fix is in the SHARED `library-browser.js`, so
  Serpe's pattern library gained it too.
- Also found: `.mc-bpm-save` declared `background: var(--mc-success)` and then
  overrode it with a hardcoded `#4a6a9a` two lines later. The token reference
  looked live and never applied. Kept the colour that actually renders.

Post-fix: **0 violations**. The remaining "incomplete" is contrast on
`aria-hidden` glyphs and OS-rendered `<select>` text.

### B3b. Workspace — audited 2026-08-02; the keyboard findings are the ones that matter

Axe on a populated Workspace (13 modules): **0 violations**, and it stayed 0
after fixes, which is precisely the point. Everything real here was invisible to
it.

Alex flagged the risk in advance: *"key bindings could play tricks with
assistive technology."* They did.

- **The trigger field was a KEYBOARD TRAP.** "press a key…" called
  `preventDefault()` on every keydown including Tab, so a keyboard-only user who
  focused it could not leave without a mouse. WCAG 2.1.2, Level A. Tab now moves
  focus, Escape clears, every other key still captures.
- **A held key fired the bound action once per repeat.** Leaning on a key
  machine-gunned it — a problem for a motor impairment, sticky keys, or an
  on-screen keyboard, and no action here means "do this forty times".
- **Eight PCS pads all announced the same thing** ("Learn: store the last scale
  heard…"), so eight identical stops with nothing to tell them apart. Same shape
  as MIDIcurator's kebabs, and Axe passes it for the same reason.
- **One heading for eighteen panels.** The modules were already `<section>`s
  with accessible names, so region navigation worked — but heading navigation is
  how most screen-reader users move, and there was only the H1. Module titles
  are `<h2>` now; 20 headings.

Deliberately NOT changed: the global handler does not `preventDefault`. A
binding OBSERVES a key rather than consuming it, so the browser and any
assistive technology keep their own shortcuts. The consequence is that a
bare-letter binding will not fire for a screen-reader user in browse mode, since
the reader intercepts those first — a gap in what they can reach, not a hazard,
and the reason a modifier is the safer thing to bind. Worth saying in the UI
eventually.

Five tests now cover the keyboard contract, verified by reintroducing the trap
and the repeat bug and watching two of them fail.

### B4. `*N` lengthening: C++ and JS now generate different material

Resolved on the JS side 2026-08-02 — `polyLaneAt` seeds from the base pattern,
so a trigger names a pattern. The C++ engine still grows `*N` with its own RNG.

D3 means the engine wins where it is present, so nothing is *broken*: a plugin
session is self-consistent and a standalone session is self-consistent. But the
same notation gives different material in the two places, and the conformance
vectors cannot pin `*N` until they agree.

**Needs a decision, not a fix:** should the seed cross over? If yes, it is a C++
change plus a vector regeneration.

### B5. `msuite jam` is promised in six documents and does not exist

`DESIGN_BRIEF`, `MASTER_PLAN`, `INTENT` (H1), `PRIORITIES`, `TRAINING_PLAN`,
`TESTING_NOTES` — and three of those are already *about* it not existing, which
is its own kind of tell. `TESTING_NOTES` puts it plainly: "The name has outlived
several answers."

Tier 0 changed the calculus. Workspace now boots as Pattern → Player → Vane
Synth, plays poly, advances progression and has a drum kit — which is most of
what `jam` was ever described as doing, in a form that already exists and is
already tested.

**Recommended: retire the name.** One line in INTENT H1 recording that Workspace
absorbed it, and remove the forward-looking promises from the other five. A
promise repeated in six places and kept in none is worse than an absence — and
the suite's own rule is that a dead-end is a bug.
